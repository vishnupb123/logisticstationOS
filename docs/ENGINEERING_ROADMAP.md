# Engineering Roadmap

> **Revision note (2026-10-31)**: this roadmap was rewritten to adopt the more detailed ten-milestone implementation plan provided directly by the project owner during the implementation-phase handoff, superseding this document's original nine-milestone (M0–M8) sketch from the architecture phase. The underlying sequencing logic is unchanged — reliable data before intelligence, a calibrated twin before RL, agents before governed coordination (`docs/PRODUCT_VISION.md` §"Capability arc") — this revision mainly adds detail, splits the original governance milestone into two (M7, M9), and adds a predictive-intelligence milestone (M8) that the vision always implied but the original roadmap never gave its own slot.

Each milestone lists a goal, deliverables, exit criteria, and explicit non-goals. A milestone is not "done" by vibes, and it does not borrow work from a later milestone. Only one milestone is attempted per working session; a session starts by checking `HANDOFF.md` and this file to identify the next incomplete milestone.

## Milestone 1 — Software foundation — ✅ complete (2026-10-31)

**Goal**: repository structure, a minimal runnable local-first backend, and a working dev loop.
**Delivered**: `backend/` FastAPI app (settings, structured logging, Postgres + DuckDB connectors, `/health` + `/health/ready`, Alembic wiring, pytest suite); `docker-compose.yml` + `backend/Dockerfile` bringing up Postgres + the API together (verified end-to-end — `/health/ready` reports both dependencies `ok` when run via Compose); `.github/workflows/ci.yml` running `ruff check` + `pytest` against a real Postgres service container on every push/PR; `backend/.env.example`; the full `docs/` architecture set and ten ADRs from the architecture phase.
**Exit criteria**: `pytest` passes locally and in CI; `docker compose up` brings up a working stack verified by hitting `/health/ready`; `ruff check .` is clean; nothing beyond this scaffold is implemented.
**Non-goals**: any domain model, event, agent, simulation, or RL code.
**Note**: `docker-compose.yml` remaps host ports to 5433/8010 (not 5432/8000) because this development machine already had unrelated containers bound to the defaults — change it back if that's not true in your environment.

## Milestone 2 — Domain model and event infrastructure — ✅ complete (2026-10-31)

**Goal**: Layer 1 + the writable half of Layer 2 (`docs/SYSTEM_ARCHITECTURE.md`).
**Delivered** (Cycle 1 slice only — truck → induct → sort → stow, as scoped, not the full entity list): SQLAlchemy domain models (`backend/app/domain/`) for Station, Truck, Aisle, Hamper, Stower, Bag, Parcel; a single append-only `events` table (`backend/app/events/`) with Pydantic-validated per-event-type payloads (`truck.arrived`, `truck.unloaded`, `parcel.inducted`, `parcel.classified`, `parcel.sort_attempted`, `parcel.jackpot_cleared`, `parcel.stowed`) and the full envelope (`event_id`, `event_type`, `entity_id`, `occurred_at`, `recorded_at`, `source`, `source_kind`, `correlation_id`, `idempotency_key`, `schema_version`, `payload`, `provenance`); an autogenerated, upgrade/downgrade-verified Alembic migration; a replay-based projector (`backend/app/services/event_ingestion.py`) that rebuilds a parcel's or truck's state from its full event history on every write — provably idempotent and order-independent (tested by shuffling the same event set and asserting identical output); a repository layer; a seeded, deterministic synthetic Cycle-1 event generator (`backend/app/services/synthetic_events.py`) and CLI (`backend/scripts/generate_synthetic_events.py`).
**Exit criteria — met**: a synthetic truck-arrival-through-stow event stream ingests, persists, and reads back idempotently (verified against a live Postgres, not mocked); duplicate/out-of-order/missing/conflicting events are handled and covered by tests (33 tests, including a "no parcel vanishes from the generated stream" conservation check); an event whose predecessor is missing or wrong is still persisted and projected from, never silently dropped, and the projection is flagged inconsistent rather than assumed correct — the concrete form of "virtual state is not assumed to match physical state."
**Scope deliberately not built**: the high-value/sideline/future-date/exception cage workflows — a non-`normal_cycle1` classification simply stops at `pending_exception`; Cycle 2 (Pick & Stage, dispatch, routes, waves, vans, returns) entities; any HTTP exposure of event ingestion (everything is a Python service call today, used directly by the generator script — no endpoint yet, since there's no real consumer for one).
**Non-goals**: analytics, agents, simulation, or UI.

## Milestone 3 — Data engineering and analytics — ✅ complete (2026-10-31)

**Goal**: the read half of Layer 2 + Layer 3's data foundation.
**Delivered**: a Parquet export of the Milestone 2 event log (`backend/scripts/export_events_to_parquet.py` → `data/processed/events.parquet`, one Postgres `events` row per Parquet row, `payload` serialized as a JSON string column); a dbt Core project (`backend/analytics/`) with layered models (`raw` → `cleaned` → `curated` → `operational_intelligence`) against DuckDB, run self-contained (`profiles.yml` lives in the project, not `~/.dbt/`); 30 dbt tests covering null values, uniqueness, referential integrity (every non-induct parcel event must have a prior `parcel.inducted`), valid event types (`accepted_values` against `app/events/event_types.py`, manually kept in sync), timestamp validity (`occurred_at <= recorded_at`), and metric-contract requirements (non-negative dwell time, non-negative jackpot backlog); all five `proposed`-status metrics from `docs/OPERATIONAL_DOMAIN_MODEL.md` §4.1 (WIPS, induct throughput, jackpot volume, parcel dwell time, stow throughput) computed as queryable DuckDB tables.
**Exit criteria — met**: ran the full pipeline against synthetic data end-to-end (seed → export → `dbt run` → `dbt test`), all 9 models built and all 30 tests passed; each metric's contract in `docs/OPERATIONAL_DOMAIN_MODEL.md` §4.1 now states its real required source events and data-quality requirements rather than placeholder prose. Sanity-checked actual computed values, not just "the SQL ran": 150 synthetic parcels → 143 `normal_cycle1` all stowed, 7 non-`normal_cycle1` correctly unstowed (`pending_exception`), jackpot diverts exactly matched clears, dwell times all positive and in a plausible range.
**Explicitly not built**: an `app/analytics` Python service or API route exposing these metrics — there's no real consumer yet (deferred to Milestone 5+/10, same reasoning Milestone 2 applied to not building an event-ingestion HTTP endpoint); incremental/partitioned Parquet export (every export is a full overwrite of one file — fine at this data volume, revisit if that changes); schema-conformance and freshness data-quality checks (nothing to check `schema_version` conformance against yet, no live consumer for whom staleness matters yet).
**Non-goals**: the organization-specific metrics still marked `requires_validation` (DEA, OTD, Sort Compliance, FPY, FSAF, Timely Staged, Route readiness) — they stay unimplemented until validated, never approximated. No dbt model duplicates application logic without a clear analytical purpose — `curated_parcel_lifecycle` restates (doesn't reuse) `event_ingestion.py`'s projection logic deliberately, since the two serve different consumers with different failure modes.

## Milestone 4 — Digital twin — ✅ complete (2026-10-31)

**Goal**: a SimPy discrete-event model of the full operational lifecycle (`docs/DIGITAL_TWIN_SPEC.md`), starting with Cycle 1.
**Delivered**: a YAML scenario-config format loaded into a typed Pydantic model (`backend/app/simulation/config.py`); a SimPy model (`backend/app/simulation/model.py`) with real resource contention — a shared induct station, a shared stower pool, and per-aisle hampers with finite capacity, where jackpot diversion **emerges from hampers actually being full**, not a probability knob (the actual value-add over Milestone 2's generator); the `normal_operations` and `delayed_inbound_trucks` scenarios (`simulation/scenarios/`), verified to produce genuinely different arrival timelines, not just different seeds; deterministic, seeded reproducibility (every random draw, including the id-generation bug class caught in Milestone 2, goes through shared helpers in `backend/app/core/determinism.py`); a conservation test suite (every simulated parcel verified via the real `event_ingestion.project_parcel` function — not a twin-specific reimplementation — to end in a terminal state, consistently).
**Exit criteria — met**: both scenarios run reproducibly (verified: identical output including `event_id`, run twice); the conservation/invariant suite passes (16 tests, `backend/tests/simulation/`); simulation output is structured to match Milestone 3's analytical table shape — verified directly, not just asserted, by running the unmodified `backend/analytics/` dbt project against simulated Parquet output instead of real data and getting the same 9 models built, 30 tests passing.
**Architectural decision made**: simulated events are written straight to Parquet, never through PostgreSQL/`EventStore` — a simulation run isn't "operational truth" (ADR-0002). Comparability with real data is achieved at the schema/dbt level (same `EventEnvelope` shape, same dbt models reading whichever Parquet file is pointed at), not by mixing simulated rows into the operational database. Recorded as a dated amendment to ADR-0006.
**Scope boundary maintained**: like Milestone 2, the high-value/sideline/future-date/exception cage workflow is not simulated — a non-`normal_cycle1` classification stops the simulated parcel at `pending_exception`, mirroring the application layer rather than inventing simulation behavior for a workflow nothing else models.
**Non-goals**: the full ten-scenario catalog, RL, or any claim that the simulator is calibrated to real-world performance — there is no real operational data to validate against, by design (`docs/DIGITAL_TWIN_SPEC.md` "Reproducibility" / ADR-0006 risk note).

## Milestone 5 — Agentic AI system — ✅ complete (2026-10-31)

**Goal**: the hierarchical agent roster from `docs/AGENTIC_ARCHITECTURE.md`, starting with one agent end to end.
**Delivered**: the orchestration state machine (`backend/app/orchestration/` — `AgentDefinition`/`AgentExecutor`, a PostgreSQL `agent_executions` audit table, one checkpoint boundary, bounded retries with per-attempt timeout, a working `resume()`); the `LLMProvider` abstraction (`backend/app/core/llm/`) with `FakeLLMProvider` (test-only) and `OllamaProvider` — the project owner's explicit choice for true local-first inference (ADR-0008 amendment), its request/response handling verified against a mocked HTTP layer since Ollama isn't installed on this machine; the Flow Intelligence Agent (`backend/app/agents/flow_intelligence/`) with its full contract filled out in `docs/AGENTIC_ARCHITECTURE.md`; `app/analytics/duckdb_queries.py` — the Python-side query interface onto the Milestone 3 analytics DuckDB file that `docs/SYSTEM_ARCHITECTURE.md` always said would arrive "once an API/agent consumer needs it."
**Exit criteria — met**: ran the complete real pipeline (synthetic generator with an elevated jackpot rate → PostgreSQL → Parquet → dbt → agent) truncated to a mid-run snapshot with a genuine, uncleared jackpot backlog (26 cumulative diverts, 8 clears, 18 still stuck) — the agent correctly reported this as an `observation` citing `metric_jackpot_volume`, plus a correctly-tagged `hypothesis` from the LLM step, with zero `recommendation`-category output anywhere. 79 tests pass (33 new this milestone), including both this exact scenario (hand-built DuckDB fixture) and the orchestration mechanics (checkpointing, retry, degrade-gracefully, resume) in isolation from the real agent.
**Structural enforcement, not convention**: the LLM-facing output schema (`LLMFinding`) is typed so `observation`/`calculated`/`recommendation` are not valid values — Pydantic rejects them, so "the LLM never computes a number the analytics layer should" and "no recommendation without Layer 5" are both enforced by the type system, not a prompt instruction trusted to hold.
**Non-goals**: the full agent roster (Station Orchestrator, Investigation, Dispatch Intelligence, Planning, Reconciliation and Returns follow once this one agent's contract pattern is proven), multi-agent orchestration, or any recommendation requiring Layer 5 approval (Layer 5 doesn't exist yet) — all still true, none built. Dynamic LLM-driven tool selection also wasn't built: `gather_evidence` always calls the same fixed five tools deterministically; nothing yet needs the LLM to choose among tools.

## Milestone 6 — Reinforcement-learning environment — ✅ complete (2026-10-31)

**Goal**: a Gymnasium-compatible RL environment for one narrow, bounded decision problem.
**Problem, as formalized**: aisle-level stow capacity and workload balancing under variable inbound flow (ADR-0007 amendment) — concretely, a priority weight per aisle, reallocated every 60 simulated seconds, governing which aisle's parcel a freed stower serves next. Required adding a real decision point to the Milestone 4 twin that didn't exist before (`StowPriorityProvider`, `app/simulation/model.py`) — the twin's stower pool was pure FIFO with no aisle concept until this milestone.
**Delivered**: the Gymnasium environment (`backend/app/rl/env.py::StowBalancingEnv`) wrapping the twin via a new `setup_simulation()` entry point that steps the SimPy simulation in small increments between policy decisions; hard constraints enforced structurally (an anti-starvation priority floor, plus the action space's own shape, which cannot express "summon more capacity") — `constraint_violations` counted per step, never a reward penalty; a static baseline and a rule-based baseline (`app/rl/baselines.py`); a PPO policy trained for 50,000 timesteps (`backend/scripts/train_rl_policy.py`); an evaluation report (`backend/scripts/run_rl_evaluation.py`) comparing all three across 5 seeds on the training scenario and two held-out scenario variations (higher volume; tighter capacity), verified byte-for-byte reproducible by re-running it.
**Exit criteria — met, with an honest result, not a success story**: the evaluation report exists, is reproducible, uses multiple seeds and held-out scenarios — and makes exactly the kind of claim the exit criteria requires it not to overreach on: PPO's reward was higher than both baselines in two of three scenarios, but its jackpot-backlog outcome (the metric that actually matters) was not better than either baseline anywhere, and its reward advantage vanished entirely on the hardest held-out scenario. Reported as a reward-design finding, not papered over. Full results: `docs/RL_ENVIRONMENT_SPEC.md`.
**A real design bug caught before training**: the first attempt at translating action weights into SimPy priorities used a full ranking (`argsort`), which meant "uniform weights" (the static baseline) never actually produced tied priorities — it silently favored whichever aisle sorted first by index. Fixed by bucketing weights into discrete priority levels so genuinely-equal weights collapse onto the same value and get real FIFO tie-breaking from the twin itself.
**A real scenario-tuning bug caught before training**: the first attempt at a training scenario (more stow capacity, a 5-minute decision interval) never actually created hamper-capacity contention — two different fixed policies produced byte-identical trajectories on the same seed. Retuned (`simulation/scenarios/rl_stow_balancing.yaml`) and reverified empirically across 5 seeds before building anything further on it.
**Non-goals, maintained**: the trained policy was not wired into any agent or anything beyond the twin (and the honest result above is exactly why not — see `docs/RL_ENVIRONMENT_SPEC.md` §"Relationship to the agentic layer"); no multi-agent RL; no real-world performance claim.

## Milestone 7 — Agent and RL coordination — ✅ complete (2026-10-31)

**Goal**: a controlled decision interface connecting the agentic layer, the RL layer, and a policy engine, without granting autonomous control.
**Delivered**: `backend/app/security/` (Layer 5, scaffolded empty since Milestone 1) is now real — `models.py` (`DecisionRecord`, one row per decision carrying context, evidence, candidates+evaluations, policy-engine result, risk evaluation, approval, and observed outcome), `repository.py` (typed create/approve/reject/record-outcome functions — the only place a `DecisionRecord`'s status is allowed to change), `policy_engine.py` (a simple, deliberately rule-based eligibility/constraint check — an explicit decision-type allow-list, plus an independent re-check of the anti-starvation floor the RL environment already enforces structurally, as defense in depth), `risk.py` (a minimal, honestly-labeled stub — every current decision type is simulation-only and therefore reversible by construction; a real blast-radius model is Milestone 9 work, per ADR-0009's own "needs its own design work" note), and `decision_service.py` (the actual coordination: evaluates named candidate interventions via a real digital-twin simulation run per candidate, runs the policy engine and risk evaluation, builds a deterministic `calculated` comparison and a `recommendation` finding — the first real use of the `recommendation` evidence category anywhere in the system, since Layer 5 now exists to approve one — and persists it all as a `DecisionRecord`, always `pending_approval`). `backend/app/rl/evaluation.py` extracts the per-seed episode-running and aggregation logic out of `scripts/run_rl_evaluation.py` so the Milestone 6 baseline report and this milestone's candidate evaluation run the identical code path, not two implementations that could silently diverge. A new Alembic migration (`57b3ef4063b0`) adds `decision_records`, upgrade/downgrade-verified. `backend/scripts/run_decision_demo.py` demonstrates the full pipeline end to end against real Postgres and real simulation runs — propose → policy-engine check → (attempted, refused) outcome-before-approval → human approval → observed-outcome simulation run — with its own printed output, verified reproducible across repeated runs (identical candidate evaluation numbers given the same fixed seeds).
**Exit criteria — met**: a full decision record (context → evidence → candidates → simulation/policy evaluation → approval → outcome) is produced and queried end to end for the shipped `rl_stow_balancing` scenario, both in `run_decision_demo.py` and in `backend/tests/security/test_decision_service.py::test_full_lifecycle_propose_approve_observe_outcome`. The "no path lets a recommendation become acted on without approval" requirement is a structural guard, not a convention: `record_observed_outcome` (`app/security/repository.py`) raises `ValueError` for any `DecisionRecord` not in `APPROVED` status — proven by a test that calls it directly on a `pending_approval` record and asserts the raise, and demonstrated live in `run_decision_demo.py` step 2.
**Deliberately did not use the trained PPO policy from Milestone 6**: given that milestone's own honest finding (PPO's reward advantage never translated into a better jackpot-backlog outcome than the baselines), citing it as a candidate here would overstate its value. The candidates evaluated are named, fixed priority-weight vectors plus the existing static/rule-based baselines — proving the coordination mechanism works independent of any one candidate being especially good, which was the actual point of sequencing Milestone 7 this way (see `HANDOFF.md`'s Milestone 6 handoff notes and `docs/OPEN_QUESTIONS.md`).
**20 new tests** (91 → 111 total): `tests/security/test_policy_engine.py` (6), `tests/security/test_repository.py` (9, all DB-dependent against real Postgres), `tests/security/test_decision_service.py` (5, running the real RL environment end to end) — plus the pre-existing suite unaffected by the `app/rl/evaluation.py` extraction (verified: all prior RL tests still pass unchanged).
**Non-goals, maintained**: RBAC/role-based approval permissions (still Milestone 9 — `approved_by` here is a plain string, not a checked role, consistent with `docs/SECURITY_AND_GOVERNANCE.md`'s own sequencing); a general risk/blast-radius model (the `risk.py` stub is explicitly not one); wiring any RL output into an agent's own output (the Flow Intelligence Agent is unchanged); autonomous operational control, under any confidence threshold — see ADR-0009, which this milestone implements, not revisits.

## Milestone 8 — Predictive intelligence — ✅ complete (2026-10-31)

**Goal**: carefully scoped predictive models, each with an honest account of its own limitations.
**Candidate areas**: inbound volume forecasting, stow bottleneck prediction, jackpot accumulation risk, route readiness prediction, dispatch delay risk, parcel reconciliation anomalies.
**Chosen first (best supported by Milestone 2-4 data)**: jackpot accumulation risk — route readiness and dispatch delay risk need unbuilt Cycle 2 data; the other three either overlap this one's state or don't fit the forecasting-shaped deliverable as naturally. Full rationale: `docs/PREDICTIVE_INTELLIGENCE_SPEC.md`.
**Delivered**: `backend/app/predictive/jackpot_risk/` — `dataset.py` (builds a labeled, per-decision-interval tabular dataset from many Milestone 4 twin episodes, with an explicit feature/label leakage boundary), `model.py` (two baselines — a base-rate predictor and a one-line current-backlog heuristic — plus a scaled logistic regression, the `predictive` extra/scikit-learn, not a base dependency), `evaluation.py` (shared accuracy/precision/recall/F1/ROC-AUC computation), `schemas.py` (`JackpotRiskPrediction` + `to_finding`, the first real conversion of a statistical model's output into the `prediction` evidence category), `predict.py` (versioned model persistence/inference). `backend/scripts/train_jackpot_risk_model.py` builds the dataset, splits it temporally by episode/seed (never shuffling rows), trains and evaluates all three candidates on held-out test episodes AND two scenario variations never trained on (the same held-out-scenario rigor `docs/RL_ENVIRONMENT_SPEC.md` applied to the RL policy comparison), and writes a reproducible evaluation report.
**Exit criteria — met**: a documented dataset (`docs/PREDICTIVE_INTELLIGENCE_SPEC.md`), temporal (seed-ordered, never-overlapping) train/test validation enforced by a function that raises on overlap, and an evaluation report with metrics and stated limitations — see the spec doc's "Evaluation protocol and results" and "Non-goals" sections.
**A real finding caught before shipping**: the first feature set included `parcels_inducted`/`trucks_remaining`, which scored a suspiciously high 0.961 accuracy/0.985 ROC-AUC. Investigated rather than reported at face value: those two features are measured at correlation -1.0 in this fixed-arrival-schedule scenario, acting as a trivial "how far into the run are we" clock rather than genuine operational signal — confirmed by the logistic regression's own coefficients, which were dominated by the clock proxy over every real operational feature. Removed from the shipped feature set; the honest result (0.783 accuracy / 0.857 ROC-AUC on held-out episodes, 0.72-0.73 ROC-AUC on held-out scenario variations — still clearly beating both baselines) is what's reported.
**Unlike Milestone 6's cautionary RL result, this is a genuine positive finding** — a simple, interpretable model beats both baselines by a wide margin using only real operational state, and degrades gracefully (not catastrophically) on scenario variations it never trained on.
**20 new tests** (111 → 131 total): dataset construction/leakage-boundary/temporal-split tests, model/baseline unit tests (including a toy-signal test that the logistic regression actually learns the right direction), evaluation-metric edge cases (single-class `y_true`, threshold sensitivity), schema/evidence-category tests, and model-persistence round-trip tests (including a stale-feature-schema rejection).
**Non-goals, maintained**: the other five candidate areas — not attempted, validating the pattern on one first per the roadmap's own non-goal; deploying this model's output as an unflagged fact anywhere (it's `prediction`-tagged, never `observation`); wiring the prediction into the Flow Intelligence Agent or `app/security/decision_service.py` (deliberately deferred, same reasoning as the RL policy in Milestones 6/7 — see `docs/OPEN_QUESTIONS.md`); a running drift-monitoring system (no live serving path exists yet — the plan is specified in `docs/PREDICTIVE_INTELLIGENCE_SPEC.md`, not implemented as code).

## Milestone 9 — Governance and reliability — ✅ complete (2026-10-31)

**Goal**: the rest of Layer 5, and cross-cutting reliability that earlier milestones deferred.
**Delivered**:
- **RBAC** (`backend/app/security/rbac.py`): `Role` (`operator`/`supervisor`/`admin`), a fixed role → eligible-decision-type permission table, `check_can_approve` (raises `RBACError`). `repository.py::approve_decision`/`reject_decision` now call it before mutating anything, and persist the claimed role (`DecisionRecord.approver_role`). Deliberately simple and code-defined — there's no real login/session system yet for a database-backed role to attach to; this checks a *claimed* role against a fixed table, the same "simple, not learned" precedent the policy engine set. Honest remaining gap: no verified identity behind the claim yet (tracked in `docs/OPEN_QUESTIONS.md`).
- **Shadow-mode evaluation**: `decision_service.py::propose_decision(..., shadow=True)` creates a `DecisionRecord` with status `shadow` — a terminal status that can never be approved, rejected, or have an outcome recorded, via the same `_require_pending`/`APPROVED`-only guards already in place (no new parallel check needed).
- **Data validation**: `repository.py::create_decision_record` now re-validates every JSONB-bound argument (evidence, candidates, policy-engine result, risk evaluation) against its real Pydantic schema (new `policy_engine.py::CandidateRecord`) before persisting — a malformed caller gets a loud `ValidationError`, not silently-corrupt audit data.
- **Model and policy versioning**: `backend/app/core/versioning.py::validate_version_format` names and checks the dated `"YYYY-MM-DD.N"` convention already used ad hoc by `POLICY_VERSION`/`MODEL_VERSION`; `DecisionRecord.component_versions` (new column) stamps every decision with the exact version of each component that produced it.
- **Secure configuration review**: `Settings.postgres_password` is now `pydantic.SecretStr`, masked out of `repr()`/`str()` by default; `.env.example`/`docker-compose.yml` reviewed, contain only placeholder values.
- **Observability**: `backend/app/core/tracing.py` — a minimal, local-first OpenTelemetry integration (`SimpleSpanProcessor` + `ConsoleSpanExporter` only, no external collector). `AgentExecutor.run`/`resume` and `decision_service.py`'s `propose_decision`/`observe_outcome` are instrumented with spans.
- **Error-handling and idempotency reviews**: both documented in `docs/SECURITY_AND_GOVERNANCE.md` — conclusion in both cases is "the existing pattern is correct," not a gap needing new code (the readiness probes' broad `except Exception` is deliberate; `AgentExecution`/`DecisionRecord` rows are deliberately non-idempotent audit-log entries, not records to dedupe).
- New migration (`8a19c7f88922`) adds `approver_role`/`component_versions` to `decision_records`, upgrade/downgrade-verified.
**Exit criteria — met**: `scripts/run_decision_demo.py` demonstrates, live, against real Postgres: an `OPERATOR` refused approval (RBAC), a `SUPERVISOR` successfully approving, and a shadow-mode decision refusing approval even for an `ADMIN` — the literal "cannot reach acted-on status without RBAC-checked human approval" and "shadow-mode runs produce output clearly labeled as not-executed" requirements, exercised rather than only asserted.
**23 new tests** (131 → 154 total): `tests/security/test_rbac.py` (6), `tests/core/test_versioning.py` (3), `tests/core/test_tracing.py` (2), plus RBAC/shadow/validation coverage added to the existing `tests/security/test_repository.py` and `test_decision_service.py`, and a version-format check added to `tests/predictive/jackpot_risk/test_model.py`.
**Non-goals, maintained**: autonomous execution of any approved recommendation against a real system — there still isn't one to act on; a real auth/identity system behind RBAC's claimed role; a general risk/blast-radius model beyond the Milestone 7 stub.

## Milestone 10 — Operational command centre — ✅ complete, both parts (2026-10-31)

**Goal**: Layer 6, a usable React/TypeScript command centre.
**Deliverables**: station overview; live-or-simulated operational state (clearly labeled which); induct and sortation; stow and jackpot; high-value processing; Pick & Stage; dispatch waves; returns; AI investigations view (evidence categories visible, not flattened); digital-twin scenario runner; RL policy comparison view; decision and audit history (backed by Milestone 7/9's records).
**Exit criteria**: every view states the source and status of each metric it shows (synthetic/simulated vs. whatever "real" means at that point) — simulated data is never presented as live operational information.

**Deliberately split into two parts, by explicit project-owner decision in a scoping conversation held before any frontend code was written**: Part 1, the API layer the frontend will consume; Part 2, the React/TypeScript frontend itself.

**Part 1 — delivered (2026-10-31)**: `backend/app/api/routes/` gained five routers — `analytics.py`, `agents.py`, `simulation.py`, `rl.py`, `decisions.py` — covering every view that has real data behind it (Cycle 2 views — high-value, Pick & Stage, dispatch waves, returns — have none; not built, not stubbed). New `backend/app/schemas/` package for HTTP-facing request/response models (populated for the first time). RBAC-gated write actions on `/decisions` (propose/approve/reject/observe-outcome), with the frontend's planned "dev-mode role picker" in mind (no real login system exists; the API already requires and checks `approver_role`, same honest limitation as Milestone 9's RBAC). CORS configured for a local Vite dev server. Two HTTP-specific security boundaries added deliberately: no endpoint accepts an arbitrary filesystem path (`scenario` is always a filename resolved against a shipped-scenario allow-list, `app/simulation/config.py::resolve_shipped_scenario_path`) or an arbitrary DuckDB path (always the server-configured one). Full reference: `docs/API_REFERENCE.md`.
**A real nuance found while building this**: `AgentExecutor`'s LLM-fallback path (Milestone 5) never persists its fallback output to the audit row — `POST /agents/flow-intelligence/run` compensates by always returning the actual in-memory result, not relying solely on what got persisted. Not changed in `app/orchestration/` itself — out of scope for this session.
**36 new tests** (154 → 190 total): `tests/api/` (29, across all five routers, including dedicated path-traversal-rejection tests), plus direct unit tests for the new `app/simulation/config.py` helpers and `app/orchestration/repository.py::list_executions`. Verified live against a real running server (`uvicorn`), not just `TestClient` — the full propose → RBAC-denied → approved → observed-outcome decision flow exercised over real HTTP.
**Part 2 — delivered (2026-10-31)**: `frontend/` — a Vite + React 19 + TypeScript SPA (no SSR, no Node server of its own), React Router for the seven views, TanStack Query for server state, and inline SVG charts (no charting library dependency). Design tokens (`src/index.css`) come from the `dataviz` skill's validated reference palette — categorical/sequential/status colors, light+dark mode. Every view carries a `DataSourceBadge` ("Synthetic data" or "Simulated run," never "live" — StationOS has no live operational system to be live against) per the exit criterion below. The decision-governance view includes the agreed dev-mode role picker (`src/components/RolePicker.tsx`), visibly labeled "not real authentication" in the UI itself, not just in docs.
**Exit criteria — met**: every view's `DataSourceBadge` states synthetic vs. simulated; nothing in the UI presents simulated/synthetic data as live.
**Four real bugs found and fixed via actually running the app in a browser** (Playwright + a downloaded Chromium, `chromium-cli` wasn't available in this environment — see `frontend/README.md`), not by reading code: (1) an SVG chart with a `viewBox` but no explicit CSS `height` rendered ~9x too tall, since the browser fell back to the viewBox's own intrinsic aspect ratio; (2) SVG `<text>` inside a `preserveAspectRatio="none"`-stretched coordinate space rendered visibly distorted/illegible — axis labels were moved to plain HTML below the SVG; (3) a stale-query-cache bug where clicking into a just-run agent execution's detail page showed "no findings" even though real deterministic findings were computed, because `AgentExecutor`'s LLM-fallback path (the real nuance Part 1 already found) doesn't persist its output — fixed by seeding the query cache with the mutation's actual result; (4) the RL Policy Comparison view defaulted to the alphabetically-first scenario rather than one from the `rl_`-tuned family, silently comparing policies on a scenario documented (Milestone 6) to never produce a meaningful difference between them.
**Non-goals, maintained**: Cycle 2 views (no data exists to show); exposing the trained PPO policy via `/rl/evaluate` (same reasoning as Milestones 6/7); a real auth/identity system behind RBAC (still Milestone 9's documented limitation — the role picker is explicitly dev-mode, not a fix for it); no permanent frontend test suite was built (the Playwright verification was scratch, removed after use — `frontend/README.md` recommends `/run-skill-generator` if browser-based verification becomes a recurring need); this was deliberately the last milestone — nothing here was built early just because "it would be nice to see something," both parts were built because they were the explicit, scoped next step.

## What's deliberately not sequenced yet

Cloud warehouse adapters (ADR-0010), Kafka-style streaming (ADR-0004), additional LLM providers beyond the first, and the full ten-scenario digital-twin catalog remain real future work but aren't placed on the roadmap above, because doing so now would sequence work ahead of the need that justifies it. Tracked instead in `docs/OPEN_QUESTIONS.md` and the relevant ADR's "revisit conditions."
